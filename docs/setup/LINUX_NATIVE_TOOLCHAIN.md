# Linux Native Toolchain Handbook

Current source target: **2048 Nova 2.0.12+2012**.

This guide focuses on the native Linux desktop toolchain. Start with [`LINUX.md`](LINUX.md) for general Flutter/Linux setup and [`TOOL_SUPPORT_MATRIX.md`](TOOL_SUPPORT_MATRIX.md) for project-wide version policy.

## 1. What a Linux Flutter desktop build needs

A native Flutter Linux build normally combines:

- Flutter/Dart;
- a C/C++ compiler toolchain;
- CMake;
- Ninja;
- pkg-config;
- GTK development libraries;
- system linker/runtime development files;
- plugin-specific native development dependencies when applicable.

The application Dart code is shared, but Flutter still compiles a Linux runner and native plugin implementations.

## 2. Verify Flutter Linux support

```bash
flutter config --enable-linux-desktop
flutter doctor -v
flutter devices
```

`flutter doctor -v` should identify the Linux toolchain status. Fix missing required native packages before editing generated runner source.

## 3. Ubuntu/Debian family baseline

A typical baseline is:

```bash
sudo apt update
sudo apt install -y \
  clang \
  cmake \
  ninja-build \
  pkg-config \
  libgtk-3-dev \
  liblzma-dev
```

Exact package names can differ across distro releases. Use the distribution's supported package manager/repositories rather than downloading random tool binaries from third-party sites.

## 4. Fedora/RHEL-family concept

Package names differ, but install equivalents for:

```text
clang or GCC C/C++ toolchain
cmake
ninja-build
pkgconf/pkg-config
GTK 3 development headers
xz/lzma development headers
```

Use current distribution documentation to map those capabilities to package names.

## 5. Arch-family concept

Install equivalents for:

```text
base-devel/compiler
cmake
ninja
pkgconf
gtk3
xz/lzma development support
```

Again, prefer supported distribution packages.

## 6. Check native tools

```bash
clang --version
cmake --version
ninja --version
pkg-config --version
```

If the project works on the reviewed CI baseline but fails on a much newer local compiler/CMake stack, reproduce against a compatible environment before changing source pins.

## 7. GTK check

```bash
pkg-config --modversion gtk+-3.0
```

If this fails, GTK runtime alone may be installed without development headers/pkg-config metadata. Install the distribution's GTK 3 development package.

## 8. Resolve Flutter dependencies

From repository root:

```bash
flutter pub get
```

Then verify no unexpected lockfile drift:

```bash
git diff -- pubspec.lock analysis_options.yaml
```

## 9. Run source quality gates first

```bash
dart format --output=none --set-exit-if-changed lib test tool
flutter analyze
flutter test
```

A Dart/analyzer failure should be fixed before debugging a later native-linker error.

## 10. Debug run

```bash
flutter run -d linux
```

This is useful for interactive development. It is not the release artifact.

## 11. Release build

```bash
flutter build linux --release
```

Flutter writes the release bundle beneath `build/linux/` using the host architecture/configuration path generated by the installed Flutter version.

Do not assume a hard-coded intermediate directory when a script can locate the documented Flutter output safely.

## 12. What to distribute

The Linux release is a **bundle**, not only one executable. It can contain:

- application executable;
- Flutter engine/runtime library;
- plugin libraries;
- application data/assets;
- ICU/other runtime data generated by Flutter.

Do not copy only the executable and expect it to work on another machine.

## 13. Inspect the bundle

Useful commands:

```bash
find build/linux -maxdepth 5 -type f | sort
file build/linux/*/release/bundle/* 2>/dev/null || true
```

For dynamic dependencies on a known executable path:

```bash
ldd path/to/nova_2048
```

`ldd` output is host-specific evidence and does not guarantee compatibility with every distribution.

## 14. Package/checksum

For qualification/distribution staging, archive the **complete release bundle** rather than a single binary.

Example after identifying the actual bundle path:

```bash
tar -czf nova-2048-linux-x64.tar.gz -C build/linux/x64/release bundle
sha256sum nova-2048-linux-x64.tar.gz > nova-2048-linux-x64.tar.gz.sha256
```

If the generated architecture directory differs, use the real path instead of blindly copying this example.

## 15. CI parity

The maintained Platform Builds workflow compiles Linux on a supported GitHub-hosted Linux runner and packages/checksums the resulting release bundle.

A local build and hosted build are complementary:

- local build helps reproduce developer-machine behavior;
- hosted build provides controlled repository CI evidence;
- neither substitutes for representative end-user distribution/runtime qualification.

## 16. Plugins

Packages such as file pickers can have Linux native implementations. A Dart dependency update may therefore change generated plugin registrants or native build/link behavior.

After plugin changes:

```bash
flutter pub get
flutter analyze
flutter test
flutter build linux --release
```

Review generated/native diffs if the dependency update changes them.

## 17. CMake errors

Typical causes:

- CMake missing/unsupported;
- stale generated build state;
- missing compiler;
- missing GTK/pkg-config dependency;
- plugin native configuration problem.

Read the first CMake configure error. Do not edit generated CMake files merely to hide a missing system dependency.

## 18. Ninja errors

If CMake configures but Ninja fails, inspect the first compilation/link command and error.

Common causes:

- missing headers;
- incompatible compiler flag;
- unresolved native library;
- stale build output;
- plugin source incompatibility.

## 19. `pkg-config` errors

If a package cannot be found, check:

```bash
pkg-config --list-all | grep -i gtk
pkg-config --modversion gtk+-3.0
```

Avoid permanently overriding `PKG_CONFIG_PATH` unless you understand which nonstandard installation must be exposed and why.

## 20. Linker errors

Undefined references usually indicate a native dependency/configuration mismatch, not a Dart type error.

Capture:

- exact failing symbol/library;
- compiler/linker version;
- Flutter version;
- plugin/dependency versions;
- distribution/version.

Compare with CI before changing platform code.

## 21. Runtime library errors

An application can compile but fail at launch due to unavailable system runtime libraries.

Use:

```bash
ldd path/to/executable
```

Look for `not found` entries.

Packaging strategy must define the supported Linux runtime baseline; a raw Flutter bundle does not magically make every system library portable across every distribution/version.

## 22. Wayland/X11 considerations

Window/input behavior can vary with desktop environment/display protocol. If a UI/input bug reproduces only under Wayland or only under X11, report that environment explicitly.

Do not claim a source fix is universal from one desktop session.

## 23. Text scaling and accessibility

Linux desktop should be tested with:

- increased system/text scale;
- keyboard-only navigation;
- focus visibility;
- high contrast where relevant;
- reduced motion;
- representative screen reader if part of the qualification environment.

Automated widget tests protect shared Flutter layout/semantics but are not Narrator/Orca/desktop accessibility evidence.

## 24. File picker qualification

Game Backup file transport uses platform handlers. Test real Linux open/save dialogs on the intended desktop environment, including:

- save;
- open;
- cancel;
- invalid file;
- oversized file;
- successful round trip.

Hosted widget tests validate application policy but not every desktop portal/provider.

## 25. Clean build — when appropriate

If generated state is suspected after a tool/plugin change:

```bash
flutter clean
flutter pub get
flutter build linux --release
```

Do not use `flutter clean` as the first response to every failure; it destroys useful incremental evidence and may mask the real cause.

## 26. Tool upgrades

Before upgrading Clang/CMake/Ninja/system libraries solely because newer versions exist:

1. identify the support/security/compatibility need;
2. record current working versions;
3. use a maintenance branch;
4. upgrade one coordinated layer where practical;
5. run full Dart tests/audits;
6. run Linux release build;
7. run other affected platform builds if shared/plugin metadata changed;
8. document the new accepted baseline only after evidence is green.

See [`UPGRADING_AND_SUPPORT.md`](UPGRADING_AND_SUPPORT.md).

## 27. Do not commit machine-specific configuration

Do not commit:

- absolute home-directory SDK paths;
- generated build output;
- personal shell profiles;
- credentials/tokens;
- private signing data;
- distro cache/package downloads.

Use source-controlled documentation/configuration that works from a clean checkout.

## 28. Useful diagnosis bundle

When reporting Linux native build bugs, include:

```bash
flutter --version
flutter doctor -v
clang --version
cmake --version
ninja --version
pkg-config --version
pkg-config --modversion gtk+-3.0
```

Also include:

- distro and version;
- desktop environment/display protocol if UI-related;
- exact command;
- first meaningful error;
- commit SHA;
- whether hosted Platform Builds succeeds on the same source.

Remove unrelated personal paths/secrets where possible.

## 29. Release boundary

A successful Linux compile proves that the configured source can build in that environment. It does **not** prove:

- runtime compatibility on every Linux distribution;
- accessibility qualification;
- long-session behavior;
- native branding review;
- package-manager-specific `.deb`/`.rpm`/AppImage/Snap/Flatpak support;
- store signing/publishing.

Those claims require their own explicit scope/evidence.
